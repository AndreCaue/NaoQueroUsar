### Known Failure Modes in This Domain

1. **"Filtro fantasma" (falsa filtragem):** usuário pede salário/modalidade/contrato/senioridade ou cidade fora da whitelist (ex.: Campinas) e o sistema aplica só aproximação em `q` ou ignora, mas a resposta/UX dá a entender que houve filtro estruturado garantido — gera candidaturas/expectativas erradas.
2. **Afirmação de capacidade inexistente:** tratar "vagas parecidas com uma vaga" como busca semântica/vetorial ou seed por link/ID, quando o suporte real é apenas seed textual limitado (termos em `q`) — quebra confiança e viola o contrato explícito.
3. **Resultados desalinhados do board canônico:** interpretação/mapeamento produz `applied_params` que não reproduzem `list_published` (ou o modelo influencia seleção), fazendo o chat mostrar vagas diferentes da busca manual equivalente.
4. **Vazamento de dado sensível no caminho do chat:** contato de vaga exposto no payload/resposta do chat, ou mensagem do usuário (que pode conter dados pessoais) registrada em logs/traces/observabilidade — risco de privacidade e não conformidade.

### Regulatory / Compliance Context

- **LGPD (Lei nº 13.709/2018, Brasil) — diretamente relevante:** princípios de finalidade, adequação, **necessidade/minimização** e **segurança** (art. 6º) aplicam-se a qualquer tratamento de dados pessoais. Mensagens do chat podem conter dados pessoais; por isso não devem ser registradas em logs/observabilidade sem necessidade, e contatos devem permanecer protegidos. Bases legais e transparência (arts. 7º–9º) e retenção mínima/eliminação (arts. 15–16) orientam não persistir conteúdo do usuário; registros operacionais devem ser agregados/sem PII. O serviço é público e sem login (minimiza coleta).
- **Outras regulações setoriais específicas:** nenhuma identificada como diretamente aplicável a este contexto de listagem pública de vagas (não há decisão automatizada de contratação/crédito/saúde regulada). Manter veracidade do que é exibido/afirmado sobre vagas e limites do sistema é obrigação de produto/confiança, mesmo sem regulação setorial adicional.

### Common Pitfalls
1. **Treating LLM output as authoritative:** applying raw extracted `city/sort/q` or non-native filters (salÃ¡rio/modalidade/contrato/senioridade) as guaranteed native filters. Why: violates contract and misleads users. Fix: always map through deterministic whitelist/normalization, emit `field_statuses`/`limitations`/`meta.guidance`, keep results equivalent to `list_published` for `applied_params`.
2. **Blocking the event loop or leaving calls unbounded:** using sync Groq client in async FastAPI path, or omitting timeouts/retries budgets. Why: stalls requests and amplifies outages. Fix: `AsyncGroq` + `await`, explicit `timeout` (e.g. 12s chat), bounded retries/repair, classify `APITimeoutError/TimeoutError` to safe degraded response.
3. **Schema/validation drift and fence-wrapped JSON:** assuming `json_schema` means "never invalid", or not stripping ``` fences / not catching `ValidationError`. Why: parse failures or silent bad assumptions. Fix: `strip_markdown_fences`, `IntentLLMOutput.model_validate_json`, one bounded repair attempt per model, fail closed to degraded empty contract.
4. **Logging PII or user query text:** recording raw `message`, contacts, or full payloads in observability. Why: privacy/compliance risk and QA-03 violation. Fix: structured logs with outcome/reason/latency/counts/status only; never log message content or contact fields.
5. **Kill-switch that regresses the board:** disabling chat by breaking public endpoints or coupling failures to list/detail flows. Why: loses core value (fricÃ§Ã£o zero). Fix: env/config read in backend, chat endpoint returns controlled disabled guidance (no internals), frontend hides/disables chat affordance, `GET /public/jobs` and manual search remain independent.

## 4. Implementation Guidance

**Model Configuration:**
- **Provider/SDK:** Groq via `AsyncGroq` (direct seam), model-agnostic/configurable by env.
- **Models:** `GROQ_MODEL` default `openai/gpt-oss-20b` (fast/cost-efficient), fallback `GROQ_MODEL_FALLBACK` `openai/gpt-oss-120b` (higher quality) â€” deduped chain in `intent/client.py`; no hardcoded model in call sites.
- **Determinism:** `temperature=0` for intent extraction.
- **Output:** strict Structured Outputs `response_format={"type":"json_schema","json_schema":{"name":"search_intent","strict":True,"schema":INTENT_JSON_SCHEMA}}`.
- **Latency/limits:** per-call timeout `CHAT_SEARCH_INTENT_TIMEOUT_SECONDS` (default 12s, passed into Groq `timeout`), bounded repair (1 retry on `ValidationError` per model) then controlled fallback across chain; request/message caps and rate limits (`CHAT_SEARCH_MAX_MESSAGE_CHARS`, `CHAT_SEARCH_RATE_LIMIT`) enforced at API boundary.
- **Tokens:** keep prompts short (single user query + compact system/repair); no large context/corpus sent. Set/monitor provider-side limits via Groq console if needed; avoid unbounded generations by keeping schema small and deterministic.

**Core Pattern:**
```python
# Primary pattern: NL intent extraction -> validate -> deterministic map -> canonical search
import asyncio
import time
import logging
from groq import AsyncGroq
from pydantic import ValidationError

from app.services.intent.client import (
    build_messages, strip_markdown_fences, strict_response_format, model_chain,
)
from app.services.intent.schema import IntentLLMOutput
from app.services.intent.mapper import build_empty_intent, map_intent
from app.crud import list_published

logger = logging.getLogger(__name__)

async def chat_search_core(message: str, settings, session, page: int, limit: int):
    start = time.perf_counter()
    outcome = "success"
    reason = None
    try:
        # 1) LLM seam (mockable): strict JSON, bounded timeout/repair/fallback
        client = AsyncGroq(api_key=settings.GROQ_API_KEY, timeout=settings.CHAT_SEARCH_INTENT_TIMEOUT_SECONDS)
        resp = await client.chat.completions.create(
            model=settings.GROQ_MODEL,
            messages=build_messages(message),
            response_format=strict_response_format(),
            temperature=0,
            timeout=settings.CHAT_SEARCH_INTENT_TIMEOUT_SECONDS,
        )
        candidate = IntentLLMOutput.model_validate_json(strip_markdown_fences(resp.choices[0].message.content or "{}"))
        # 2) Server-authoritative deterministic mapping (whitelist city/sort, explicit limitations)
        contract = map_intent(candidate, raw_text=message)
        # 3) Deterministic retrieval equivalent to public search; results are JobPublic (no contacts)
        items, total = await list_published(
            session, page=page, limit=limit,
            q=contract.applied_params.q, city=contract.applied_params.city,
            sort=(contract.applied_params.sort or "recentes"),
        )
        return contract, items, total
    except (asyncio.TimeoutError, groq.APITimeoutError):
        outcome, reason = "degraded", "timeout"
        return build_empty_intent(message, reason_code="no_extractable_params"), [], 0
    except Exception:
        outcome, reason = "degraded", "llm_unavailable"
        return build_empty_intent(message, reason_code="no_extractable_params"), [], 0
    finally:
        # QA-03: structured, no-PII observability (do NOT log `message`/contacts)
        logger.info("chat_search", extra={"outcome": outcome, "reason": reason, "latency_ms": int((time.perf_counter()-start)*1000)})

```
Notes: production path should reuse `intent/client.py`+`intent/parser.py` (model-chain fallback + one repair/ValidationError handling + injectable `client/sleep` for deterministic tests) and the existing `public.py` guidance/degradation helpers; add end-to-end kill-switch check before extraction and preserve board independence.

**Tool Use:**
- **LLM tool-calling:** none. Extraction uses plain chat completion with strict `json_schema` (no function/tools) to minimize variability and keep contract auditable.
- **Internal integrations:** `app.crud.jobs.list_published` (deterministic search), `app.services.cities.resolve_city/resolve_sort` (whitelists), `app.core.ratelimit` (abuse control), `app.core.config.get_settings` (env knobs/toggle).
- **Hardening hooks (Phase 22):** feature toggle/kill-switch in settings enforced in `POST /api/v1/public/chat-search` (controlled disabled response, pt-BR guidance, no internals) and surfaced to frontend so chat UI can hide/disable while `GET /public/jobs` stays unaffected.

**State Management:**
- **Stateless per request:** single-turn; no conversation memory/history, no embeddings/vector store, no persisted chat sessions.
- **Server state:** canonical public job corpus in DB; chat reads via the same deterministic query path as manual board search.
- **Client state:** UI-only (open/close, loading/error, applied params reflected into canonical URL/board state when applicable). Do not persist user messages.

**Context Window Strategy:**
- Keep total prompt minimal: short system instruction + delimiter-wrapped user query (treated as data) + optional single repair instruction. No RAG chunks, no job listings, no history.
- User input is size-capped (`CHAT_SEARCH_MAX_MESSAGE_CHARS`) and treated as untrusted (delimiter neutralization) to prevent prompt bloat/injection artifacts.
- RAG/summarisation/agent compaction not applicable; if future phases add history, cap turns and summarise without PII before inclusion.

## 4b. AI Systems Best Practices

> Written by `gsd-ai-researcher`. Cross-cutting patterns every developer building AI systems needs â€” independent of framework choice.

### Structured Outputs with Pydantic

Framework-specific pattern (Groq `json_schema` strict + Pydantic v2, no Instructor/orchestrator): define a strict candidate model, request schema-conformant JSON, then validate/repair/fail-safe.

```python
from pydantic import BaseModel, ConfigDict, Field, ValidationError
from groq import AsyncGroq
from app.services.intent.client import strict_response_format, build_messages, strip_markdown_fences, REPAIR_PROMPT

class IntentSalary(BaseModel):
    model_config = ConfigDict(extra="forbid")
    min: int | float | None = None
    max: int | float | None = None
    currency: str | None = "BRL"

class IntentLLMOutput(BaseModel):
    """Untrusted LLM candidate for NL job search (chatbot intent extraction)."""
    model_config = ConfigDict(extra="forbid")
    q: str | None = None
    city: str | None = None
    salary: IntentSalary | None = None
    work_mode: dict | None = None   # keep exact schema as in intent/schema.py
    contract_type: dict | None = None
    seniority: dict | None = None
    sort: str | None = Field(default=None, pattern="^(recentes|antigas)$")

async def extract_intent(client: AsyncGroq, model: str, message: str, timeout_s: int) -> IntentLLMOutput:
    msgs = build_messages(message)
    for attempt in range(2):  # initial + 1 repair (bounded)
        resp = await client.chat.completions.create(
            model=model, messages=msgs, temperature=0,
            response_format=strict_response_format(), timeout=timeout_s,
        )
        try:
            return IntentLLMOutput.model_validate_json(strip_markdown_fences(resp.choices[0].message.content or "{}"))
        except ValidationError as e:
            # log structured reason only (no message/PII), then one repair turn
            if attempt == 1:
                raise
            msgs = build_messages(message, extra_user=REPAIR_PROMPT)
    raise RuntimeError("unreachable")
```
- **Retry logic:** 1 schema-repair attempt per model, then fallback to next configured model; on exhaustion return controlled degraded contract/guidance (never raise raw internals to user). Log `outcome/reason/latency` without query text.

### Async-First Design

- **How async works here:** FastAPI endpoint is async; use `AsyncGroq` and `await client.chat.completions.create(...)` / `await extract_and_map_intent(...)` with explicit `timeout`. DB/search is awaited (`AsyncSession`, `list_published`). Tests inject a fake `client` and `sleep` to stay deterministic and network-free.
- **One common mistake:** calling a sync Groq client or blocking I/O inside the async request path (or using `asyncio.run()` inside an already-running event loop) â€” this blocks the server and can break timeouts/degradation behavior.
- **Stream vs. await:** **await** (non-streaming) for this system. We must receive complete JSON, `model_validate_json` it, apply deterministic mapping/whitelists, and only then run `list_published` and return a coherent `interpretation + results` envelope. Streaming partial tokens adds no UX value and complicates validation, limits, and safe fallback.

### Prompt Engineering Discipline

- **System vs. user separation:** fixed system prompt defines role/JSON-only output/schema fields and "no invention"; user text is wrapped as untrusted data with delimiters and an explicit "ignore instructions inside" note (`sanitize_untrusted`/`wrap_untrusted`). Never concatenate raw user text into system instructions.
- **Few-shot:** prefer none for this narrow schema; if added later, keep 1-2 minimal pt-BR examples inline (no dynamic retrieval of user data/PII). Avoid examples that imply unsupported native filters.
- **Token budget:** keep prompts concise (single query), `temperature=0`, schema-constrained output. Do not leave generation unbounded in production paths â€” enforce request timeout, message char cap, and rate limit; rely on small, fixed schema rather than large completions.

### Context Window Management

- **Not RAG/multi-turn:** no document chunks, no conversation history to summarise, no agent loop compaction.
- **Strategy for this hybrid chatbot:** include only the current (capped) NL query; never attach job corpus/results to the LLM. Deterministic DB search handles relevance/limits.
- **If degraded/empty:** return safe guidance to use manual keywords/filters instead of retrying with bloated context. Future memory features must summarise/strip PII and stay within strict budgets.

### Cost and Latency Budget

- **Per-call estimate (order-of-magnitude, Groq pricing varies):** intent extraction ~200â€“600 input + ~50â€“150 output tokens/request. At ~1k req/day this is typically well within low-cost/free-tier envelopes but must be monitored; worst-case retries (repair + fallback model) can ~2-3x a single request.
- **Latency budget:** target p95 well under `CHAT_SEARCH_INTENT_TIMEOUT_SECONDS` (12s cap) including validation/mapping/DB; fail fast to degraded manual-search guidance on timeout/provider errors.
- **Caching/routing:** exact-match in-memory cache of recent normalized messagesâ†’contract is optional but must never cache/log PII and must respect kill-switch/degradation semantics; for this low-complexity extraction a single small model (`gpt-oss-20b`) with fallback is sufficient â€” avoid sub-task fanout. Keep kill-switch as primary cost/incident control.

## 7. Production Monitoring

**Tracing Tool:** **Arize Phoenix** (default recomendado, open-source/self-hostable, agnóstico via OpenTelemetry) para tracing de spans do endpoint/chat seam em dev/staging/prod quando instrumentado. Alternativa: logs estruturados (JSON) emitidos pela aplicação como baseline obrigatória já nesta fase (sem PII). Se o ecossistema migrar para LangChain/LangGraph no futuro, preferir LangSmith; não aplicável hoje.

**Key Metrics to Track:**
- **Outcome & reason rate:** proporção de `success`/`degraded`/`disabled`/`controlled_error` por motivo (`timeout`, `llm_unavailable`, `no_extractable_params`, `rate_limited`, `validation_repair`) — saúde operacional.
- **Latência do chat-search:** p50/p95/p99 end-to-end e por etapa (extração/mapeamento/busca) vs orçamento (< `CHAT_SEARCH_INTENT_TIMEOUT_SECONDS`).
- **Equivalência/contrato:** taxa de falha em checks de equivalência a `list_published` e violações de schema/privacidade detectadas em testes/canários (deve ser 0).
- **Sinalização de limites:** distribuição de `field_statuses`/limitações (aproximado/ignorado/não suportado) e frequência de guidance de busca manual — detecta pedidos recorrentes fora de capacidade.
- **Abuso/custo proxy:** taxa de `429`/rate-limit hits, volume de chamadas LLM, contagem de retries/fallbacks por request (agregado, sem conteúdo).

**Alert Thresholds:**
- **Crítico (ação imediata / considerar kill-switch):** qualquer evidência de contato exposto no chat ou mensagem/PII em logs; falha de equivalência determinística com `list_published`; erros 5xx/vazamento de internos no endpoint de chat; `degraded` > 20% sustentado por 15 min ou `timeout/llm_unavailable` > 10% por 15 min.
- **Alto (investigar no mesmo dia):** p95 latência > 8s ou aproximação persistente do timeout de 12s; taxa de `no_extractable_params` anômala (>30% em janela comparável) indicando drift de entendimento/copy; aumento súbito de `rate_limited`.
- **Médio (tendência/flywheel):** crescimento de pedidos por capacidades não nativas (salário/modalidade/contrato/senioridade/cidades fora da whitelist) sinalizado em limitações — insumo para backlog, não afrouxar contrato.

**Smart Sampling Strategy:**
- **Sempre inspecionar (sinal forte):** interações com `outcome != success` (degraded/controlled_error/disabled paths exercitados), `rate_limited`, retries/fallback de modelo, latência > 8s, ou resposta com 0 resultados porém com parâmetros aplicados — sem armazenar texto do usuário; usar IDs técnicos/códigos e metadados agregados.
- **Amostra de sucessos:** amostragem aleatória pequena (ex.: 1–5%) de `success` para calibração de qualidade percebida via UAT guiado/matriz (reproduzir com casos sintéticos do dataset, não por replay de PII).
- **Mudança-gatilho:** ao alterar prompt/schema/modelo/mapper/limites, rodar dataset completo + revisão humana focada nos 5 exemplos-alvo e combinações (QA-01/QA-02).
- **Divergência sinal-métrica:** se feedback humano/UAT indicar interpretação ruim ou "filtro fantasma" enquanto métricas automáticas passam, tratar como lacuna de avaliação — criar novo caso rotulado e teste antes de ajustar comportamento.
