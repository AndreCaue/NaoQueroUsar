Mecânica do slowapi 0.1.10 (verificada no wheel):
- O decorator exige um parâmetro chamado `request` na função; o `Limiter` injeta os headers `RateLimit-*` só se a rota declarar `response: Response` (opcional aqui).
- O bucket é por **URL** (`key_style="url"` padrão) → rotas diferentes = buckets diferentes (D-08 ✓).
- `limiter.limit(callable)` re-resolve o callable **a cada request** → `reveal_limit()` lê o env em tempo de execução.
- A ordem dos decorators é: `@router.post(...)` por cima, `@limiter.limit(...)` por baixo (é o que registra o wrapper no FastAPI).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Visitante → rota de reveal | Input anônimo (UUID + token) cruza a fronteira pública; o contato é o dado sensível |
| Rota de reveal → Cloudflare | O token do visitante é avaliado por terceiro; o segredo fica no backend |
| Rota de reveal → banco | O contato é lido de uma linha que precisa ser `published` e não expirada |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-09 | I (Info Disclosure) | `ContactRevealResponse` | mitigate | O contato só existe neste schema; `JobPublic`/`JobListResponse` seguem sem campos de contato e há teste que garante isso (caso 10) |
| T-03-10 | E (Elevation of Privilege) | rota de reveal | mitigate | O token é validado server-side com `expected_action="reveal"` — um token de `login` não abre a rota de reveal (caso 7) |
| T-03-11 | S (Spoofing) | 404 antes do 403 | mitigate | `get_published` exige `status='published' AND expires_at > now()`; vaga pendente/expirada não vira contato |
| T-03-12 | D (DoS) | chamadas ao Siteverify | mitigate | A busca da vaga vem antes da verificação (D-03) — UUID falso não gasta cota da Cloudflare; o rate limit por IP fecha o resto (D-05) |
| T-03-13 | T (Tampering) | `idempotency_key` | mitigate | `uuid4()` novo por submissão: o servidor não aceita reuso de chave para "aproveitar" uma validação anterior |
| T-03-14 | R (Repudiation) | 403/429 | mitigate | Error-codes do Siteverify entram no log estruturado (plano 03-02) e o 429 sai com `Retry-After` — o bloqueio é auditável e explicável ao usuário |
</threat_model>
