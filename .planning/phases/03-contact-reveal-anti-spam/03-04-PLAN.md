<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Navegador do admin → `/api/v1/auth/login` | senha + token; único caminho para o JWT do master |
| `/api/v1/auth/login` → Cloudflare | o token é avaliado por terceiro antes de qualquer comparação de senha |
| Frontend → `NEXT_PUBLIC_TURNSTILE_SITE_KEY` | chave pública do widget (não é segredo); o segredo nunca chega ao browser |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-15 | E (Elevation of Privilege) | `/api/v1/auth/login` | mitigate | `authenticate_password` só é chamado **depois** do Turnstile passar (D-17) — sem token válido não há comparação de senha; teste `test_login_turnstile_failure_does_not_reach_password_check` |
| T-03-16 | S (Spoofing) | reuso de token entre fluxos | mitigate | `expected_action="login"` no Siteverify — um token mintado para `reveal` é rejeitado com `action-mismatch` → 403 |
| T-03-17 | I (Info Disclosure) | widget no browser | mitigate | O front recebe **apenas** a site key (pública por definição); o `TURNSTILE_SECRET_KEY` vive só no backend e o `/health` não o expõe |
| T-03-18 | T (Tampering) | token consumido reenviado | mitigate | `onExpire`/`onError` limpam o `cfToken`; um login falho remonta o widget (`key` nova) → token novo; o botão fica desabilitado sem token |
| T-03-19 | D (DoS) | brute force de senha | mitigate | Rate limit por IP no login (`5/minute` default, D-06) + Turnstile incondicional (D-15) — o atacante paga uma chamada à Cloudflare por tentativa |
| T-03-20 | R (Repudiation) | tentativas de login | mitigate | Error-codes do Siteverify entram no log estruturado e o 429 responde com `Retry-After` — a tentativa é registrada e explicável |
</threat_model>
